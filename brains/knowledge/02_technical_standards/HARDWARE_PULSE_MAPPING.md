# 硬體脈衝與虛擬資產對應架構 (Hardware Pulse Mapping)

> **版本**: 1.0  
> **最後更新**: 2026-05-08  
> **狀態**: 架構定案 (Approved)  
> **適用範圍**: HQ, OwnerOps (iot.tg25.win), FirmwareOps (ESP32)

## 📌 1. 架構核心原則 (Core Principles)
為解決不同原廠遊戲機主機板通訊協議複雜且不互通的問題，本系統採取「防禦性硬體隔離」策略。

### 1.1 脈衝即真理 (Pulse is Truth)
- ESP32 僅作為「數位 I/O 計數器」與「繼電器觸發器」。
- 系統絕對不介入遊戲內部機率與主板設定。所有上分、退彩、營收統計，皆以採集到的「入金表 (Coin-In)」與「出金表 (Payout)」之硬體脈衝跳動為唯一真理。

### 1.2 虛實同源同帳 (Virtual & Physical Sync)
- 玩家於手機端掃碼要求扣款上分時，系統透過 MQTT 要求 ESP32 驅動實體繼電器送出脈衝。
- 開分脈衝發生後，**實體入金表必定跳動**。ESP32 採集此跳動訊號後傳回雲端。雲端依據此「物理跳動」結算最終營收。這徹底解決了虛擬扣點與實體帳目有落差的稽核盲區。

## ⚙️ 2. 機台參數配置設計 (Node Parameter Schema)

每台註冊於 `iot.tg25.win` 的設備 (`Nodes`) 皆須在後台擴充以下參數表，以將硬體脈衝轉換為財務單位：

| 參數名稱 (Code) | 說明 | 範例設定值 |
| :--- | :--- | :--- |
| `pulse_to_token` | 入金表跳 1 下，代表多少代幣收入 | `1` (1 脈衝 = 1 代幣 = 10元) |
| `pulse_to_display` | 入金表跳 1 下，機台上顯示多少分 | `100` (方便於前端介面顯示換算給玩家看) |
| `out_pulse_to_ticket`| 出金表跳 1 下，發配多少虛擬彩票 | `1` (1 脈衝 = 給予玩家 1 張虛擬彩票) |
| `direct_prize_cost` | 出金表跳 1 下，等值多少營運成本 | `500` (專供娃娃機等直出實體商品之設備使用) |

*(註：為規避法規風險，系統中皆不標示法幣符號，全面使用 Tokens, Tickets, Pulses, Points 等代稱)*

## ⚡ 4. 訊號極性自適應 (Signal Polarity Adaptation)

為適配市面上不同品牌的遊戲機主板（如 kingapple 與 Huga），採集卡必須處理物理電平的「反向」邏輯。

### 4.1 極性定義與硬體反向
根據 `HARDWARE_NOTES.md`，ESP32 端採用 **Pull-up (上拉)** 電阻設計。當光耦 (Optocoupler) 導通時，GPIO 會被拉至 **GND (0V)**。

| 機台類型範例 | 極性模式 (Polarity) | 設備觸發狀態 | ESP32 GPIO 變化 | PCNT 捕捉邊沿 |
| :--- | :--- | :--- | :--- | :--- |
| **kingapple** | `active_high` (高電平) | 平常不導通，觸發時導通 | `1` (High) → `0` (Low) | **下降沿 (NEGEDGE)** |
| **Huga** | `active_low` (低電平) | 平常導通，觸發時不導通 | `0` (Low) → `1` (High) | **上升沿 (POSEDGE)** |

### 4.2 自適應與防呆機制
1. **開機自動偵測**：系統上電後延遲 500ms，連續取樣 5 次（間隔 10ms），若電位一致則視為靜止電位，自動判斷極性並寫入 NVS。
2. **NVS 持久化**：一旦判定或手動設定，極性將鎖定於非易失性記憶體，除非接收到重置指令。
3. **MQTT 遠端覆寫**：維運人員可透過 `set_signal_polarity` 指令強制更正極性設定。

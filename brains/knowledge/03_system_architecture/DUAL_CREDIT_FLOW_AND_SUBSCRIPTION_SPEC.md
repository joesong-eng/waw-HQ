## 1. 架構核心思想：晶片採集硬體 vs 遊戲機業務控制 之「徹底解耦」

在 WAW 2.0 體系中，無論機台是「電腦型線上主機（如小猴）」還是「傳統機板型單機（MCU/ROM Board）」，均嚴格遵守以下分工原則：

1. **採集卡（ESP32-S3）的本質**：
   - 是**透明邊緣通訊與控制中繼（Transparent Relay & Controller）**。
   - 不干涉遊戲幣值、不換算脈衝比例、不計算營業額。
2. **SignalHub 的本質**：
   - 是**信號調度中心與安全交付樞紐**。
   - 負責邊緣事件校驗、防偽重放、Webhook 冪等派發 (0s/3s/6s 重試)、對帳定案。
3. **入出金的真正權威來源**：
   - 業務開洗分與入出金的確認，**永遠來自計數器實質跳動** 或 **第三方遊戲商伺服器回傳之 `actual_points`**。

## 2. 兩種機台型態之開洗分經絡拓撲（精準釐清）

```
========================================================================================
【形態 A：電腦型網路主機 (如小猴團隊)】
========================================================================================
[現場按鍵] ──(UI1 觸發通報)──> [採集卡] ──(MQTT)──> [SignalHub 伺服器]
                                                           │
                                                 (Webhook POST 派送)
                                                           ▼
[現場遊戲電腦] <──(加分/寫分完成)── [遊戲商伺服器 (小猴)] ──(回傳 actual_points: 1000)──┘
      │
      └──(若有外接機械碼表跳表)──> [採集卡 UI3/UI4] ──(日結審計對帳)


========================================================================================
【形態 B：傳統機板型單機 (雙軌：現場硬體閉環 vs 手機遠端掃碼)】
========================================================================================
[軌道 1：現場實體按鈕] ──(純硬體接線直通)──┐
                                          │
[軌道 2：手機掃碼開分]                     ▼
 [玩家手機] ──> [Server] ──(MQTT指令)──> [採集卡UO繼電器] ──> [機板開分接點 (硬體上分)]
                                                                     │
                                                              (機板內部加分)
                                                                     ▼
                                                          [實體碼表/光耦計數器]
                                                                     │ (物理脈衝方波)
                                                                     ▼
                                                          [採集卡 UI 採集通道]
                                                                     │
                                                          (MQTT raw_value 上報)
                                                                     ▼
                                                          [Server 營收結算定案]
========================================================================================
```

### 2.1 形態 A：電腦型網路主機（小猴模式）
- **按鍵角色**：現場開分按鈕**不直接連電腦**，而是接到採集卡輸入腳位（UI1），採集卡只通報觸發事件（delta=1）。
- **經絡走勢**：採集卡 ➔ MQTT ➔ SignalHub ➔ Webhook POST ➔ 小猴伺服器。
- **加分與定案**：小猴伺服器控制電腦主機寫分，並在 HTTP 200 回調中回傳 `actual_points: 1000`。

### 2.2 形態 B：傳統機板型單機（現場純硬體閉環 vs 手機遠端掃碼）
- **軌道 1：現場實體按鈕（完全離線硬體閉環）**：
  - 服務員按下機台現場開分按鍵，**不需要通報 Server**。
  - 按鍵訊號直接導通機板開分線路上分，完全走現場電氣閉環，零網路延遲。
- **軌道 2：手機掃碼遠端開分（雲端賦能通道）**：
  - 玩家以手機掃描機台 QR Code 進行會員線上開分 ➔ Server 扣點成功後發布指令 ➔ 採集卡 UO 輸出端（繼電器/光耦）閉合，代點機板開分接點完成上分。
- **入金權威結算**：
  - 無論來自軌道 1 還是軌道 2，機板一旦上分，必定驅動實體電磁計數碼表/光耦跳動。
  - 採集卡 UI 通道忠實捕捉物理方波，將累計里程 `raw_value` 上報 Server，作為**不可篡改的唯一營收與審計真理來源**。

## 3. 收費卡點（Subscription Enforcement Gate）的精確差異

根據兩種機台型態之本質差異，收費攔截點的實作策略如下：

```
                                  ┌── 形態 A (電腦型/小猴) ──> 【卡點 A：阻斷 Webhook 派發】
                                  │
[訂閱狀態：未繳費 / Expired] ──────┤
                                  │
                                  └── 形態 B (傳統機板型)  ──> 【卡點 B：阻斷手機掃碼遠端開分 (UO 禁用)】
                                                                (現場實體鍵仍通，但無法享受遠端營運賦能)
```

### 3.1 形態 A（電腦型機台）：阻斷 Webhook 派發
- **機制**：採集卡事件照常入庫，但 SignalHub **凍結向第三方（小猴）派發 Webhook**。
- **效果**：遊戲商主機收不到開分通報，無法替現場電腦寫分，機台完全無法運作。
- **殺傷力**：★★★★★（100% 業務停擺，倒逼付費）。

### 3.2 形態 B（傳統機板型）：阻斷遠端開分（手機掃碼通道）
- **機制**：
  - 現場若有人按實體按鈕，硬體依然能上分跳表，採集卡依然記錄碼表里程（**保證帳目不丟失**）。
  - 但 **手機掃碼開分全面鎖死**（Server 拒絕開分請求，禁止下發 UO 驅動指令）。
  - **後台報表與遠端管理**：標記為過期欠費，限制部分報表匯出與進階分析。
- **殺傷力**：★★★★☆（無法進行無人化手機營運、無法使用會員遠端扣點，退化為純傳統呆機）。

## 4. 訂閱標的與商業計費模式設計

### 4.1 訂閱標的：以「實體晶片採集卡（Device / Chip ID）」為核心單元

- **最小計費顆粒**：單一 `chip_id`（例如 `3c0f02d42720`）。
- **訂閱狀態定義**：
  - `active`（正常付費中）：全功能開放。
  - `in_grace`（寬限期，預設 3 天）：發送續約告警，通訊通道正常。
  - `expired`（已過期）：
    - **採集卡物理在線監控**：保持（綠燈）。
    - **碼表物理防弊計數**：保持入庫（防弊與稽核永續）。
    - **形態 A**：Webhook 派發阻斷。
    - **形態 B**：手機掃碼開分（UO）阻斷。

### 4.2 試用期與量產過渡機制

- **新卡出廠試用（Trial Period）**：
  - 新燒錄上線的採集卡，綁定後自動贈送 **14 天免費試用期**（`expires_at = now() + 14 days`）。
  - 目的：提供技術團隊（如小猴團隊）完成硬體安裝、接腳對位、Webhook 聯調測試。
- **正式運營月費**：
  - 試用期滿後，轉入標準機台訂閱費（定價 1,200 元 / 台 / 月）。

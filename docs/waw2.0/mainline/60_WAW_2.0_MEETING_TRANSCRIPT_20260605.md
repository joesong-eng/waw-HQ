## 📅 第二階段：「人」與「物」物理專案拆分決策

**【User 提案】**
> 我的想法是，還要把比如說用戶有好幾種角色，包含訂閱、分潤的功能；場地/機台是首次註冊要設置，以後都是採集與觸發，場地是篩選分類用途。是不是至少把「人」和「物」分開成兩個子專案？你覺得呢？

**【HQ 評估與設計】**
這個想法完全切中了微服務設計中 **DDD (Domain-Driven Design)** 的核心精髓。「人與物分離」在架構上非常合理，也是最優解：
1. **負載分離**：
   - **「物」網域 (waw-iot)**：高頻寫入、低延遲、高併發（ESP32 採集、心跳、開分中繼）。資料庫為 `waw_infra`。
   - **「人」網域 (waw-business)**：低頻操作、高安全性、強事務（註冊、付費訂閱、分潤合約、對帳）。資料庫為 `waw_core`。
2. **解決網頁與前端頁面分開的頭痛點（User 反饋）**：
   - **「單一入口，後端分流」**：前端畫面（網站）絕對不需要分成兩個站點。用戶仍從同一個網址 `https://iot.tg25.win` 登入。
   - **Nginx 反向代理分流**：
     - 常規後台業務（人、訂閱、分成合約）：走 `/` 或 `/admin/*`，Proxy 至 `waw-business` 服務 (Port 8001)。
     - 高頻物聯網與開分採集 API：走 `/api/iot/*`，Proxy 至 `waw-iot` 服務 (Port 8002)。
   - **Redis 狀態快取**：當商戶在 `waw-business` 繳費續期，直接寫入共享 Redis 狀態；`waw-iot` 判斷連線或開分時，只以 $O(1)$ 的速度讀取 Redis 快取，極速響應，絕不卡死。

## 📅 第三階段：從「監控系統」轉型為「事件平台」與「軟性限制」

**【User 提問】**
> 這樣就清晰多了。然後一開始的事件型態，有包含在這次的修改吧？
> 月租與訂閱狀態決定機器是否能正常通訊與掃碼，這件事要再深思熟慮。因為是在營業，老闆如果因為非用慢交一天就不能營業的話會出事的。所以可以後台警示、LINE 頻繁通知一些手段，可以限制不能做結帳之類的，但不能影響營業。概念就是：繼續使用就開始欠我錢，欠我的錢就要還。我們繼續服務就繼續欠我錢，但是不要主動不服務，不要變成絕對。

**【HQ 決策與文檔落地】**
這是一個極具商業智慧的重大修正！我們將其定義為 **「寬限與欠費累計制 (Soft Arrears & Alert Mechanism)」**，並徹底修正了 `WAW_2.0_ARCHITECTURE_SPEC.md` 與 `V9_SYSTEM_SPLITTING_DESIGN.md` 中原有的「硬性攔截」邏輯：

1. **營運不中斷**：即使機器處於 `arrears` (欠費) 狀態，MQTT 通訊依然放行連線，玩家掃碼付款開分照常通過，不向玩家展示任何欠費警告。
2. **欠費累計機制**：每天 Cron Job 檢查，按天折算月租並累加至商戶的欠款總額中（`users.outstanding_amount`）。下次續費或提現時，系統自動先扣除欠款。
3. **後台限制與 LINE 催收**：
   - 限制後台的「交班結算」、「提現出金」與「高級報表」查看。
   - LINE Notify 或簡訊每日催付。
4. **事件型態聯動**：
   - `EVT_ONLINE` / `EVT_OFFLINE` (在線與 LWT 離線事件)。
   - `EVT_PULSE_DETECTED` (物理脈衝投幣事件，即時固化分潤寫入交易流水)。
   - `EVT_SUBSCRIPTION_EXPIRED` (訂閱過期事件，軟性聯動變更 Redis 快取)。
   - `SessionTerminated` (WebSocket 廣播強終會話)。

### 1. 當前 API 功能清單 (All Current API Endpoints)
- **`/api/internal/kiosk/...`** - 內部 Kiosk 事件回報與 Callback。
- **`/api/v1/audit/report`, `/api/v1/event/pulse`** - iHub 帳務稽核與脈衝上報（Verify iHub Token）。
- **`/api/v9/radar/devices`, `/api/v9/realtime/devices`** - 設備在線與心跳雷達。
- **`/api/v9/devices`, `/api/v9/parameter-templates`** - 設備參數與模版管理。
- **`/api/v9/venues`, `/api/v9/venues/{venue}/staff`** - 場地與人員指派。
- **`/api/v9/profit-sharing/proposals`** - 多租戶分潤提案與審核。
- **`/api/v9/notifications`** - 系統通知與 LINE 綁定 (`/line/generate-binding-code`)。
- **`/api/v9/subscription`** - 訂閱狀態與計畫管理。
- **`/api/v9/billing`** - 帳單審批與水單證明上傳。
- **`/api/v9/ota/...`** - 遠端韌體升級。
- **`/api/v9/machine/machine_info/{chip_id}`** - 機台基礎資訊查詢。

### 2. 命名與變數唯一真理 (Naming Authority Alignment)
任何 Agent 在實作代碼或 API 時，**必須以 `brains/knowledge/NAMING_AUTHORITY.md` (名稱定義來源表) 作為命名之最高真理**，絕對禁止私自創立替代名稱。
* **邏輯機台 ID (node_id)**：
  - 遊戲機：統一使用 `device_NNN` (全小寫，例如 `device_001`)。
  - 兌幣機：統一使用 `kiosk_NNN` (全小寫，例如 `kiosk_000`)。
* **物理晶片 ID (chip_id)**：統一為小寫無冒號 12 碼 hex 格式 (如 `e072a1f73a78` 或 `iot002`)。在資料庫中對應 `esp32_mac`。
* **別名規則**：僅在 API 參數中允許 `kiosk_id` 做為兌幣機 `node_id` 的別名。
- **晶片 ID**：統一命名為 `chip_id` (全小寫，無冒號的 12 碼 MAC)。❌ 禁用：`chipId`、`mac`、`esp32_mac`。
- **機台 ID**：統一命名為 `node_id`。❌ 禁用：`kiosk_id`、`nodeId`。
- **交易 ID**：統一使用 `transaction_id`。
- **脈衝計數與指令** (依據 TECHNICAL_NAMING_AND_PAYLOAD_STANDARD.md)：
  - 設備上報脈衝事件使用 `type` 與 `value` (如 `{"type":"credit_in","value":1}`)。
  - 遠端開分/洗分指令參數使用 `count` (如 `{"params":{"count":5}}`)。
- **台幣金額**：統一使用 `amount`。⚠️ **金額整數元原則**：金額傳遞必須為整數，不允許帶小數點。
- **Header 驗證**：內部 Webhook 使用 `X-Internal-Key: v9-internal-key-2026`。
